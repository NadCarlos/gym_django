# Agent Guide

This repository is the CERMED backoffice system for a medical/rehabilitation business in Río Cuarto, Córdoba. It is a Django monolith served locally with Docker Compose and in production with Gunicorn + Nginx.

## Project shape

- Runtime stack: Python 3.10, Django 4.1.12, MySQL 5.7, Docker Compose, Gunicorn, Nginx.
- Django entrypoint: `gym/manage.py`.
- Main settings module: `gym/gym/settings.py`.
- Domain apps:
  - `administracion`: patients, professionals, plans, quotas, payments, health insurance, services and administrative agendas.
  - `rehabilitacion`: rehabilitation patients, treatment/professional assignment, reports, physiotherapy agendas and appointments.
  - `finanzas`: beneficiaries, purchase/payment orders and sales book flows.
  - `entrada`: attendance/check-in flows.
  - `usuarios`: user-facing auth and user management templates/views.
  - `home`: shared home UI, static assets and template tags.
  - `utils`: shared decorators, permissions and role helpers.

Read `CONTEXT.md` before changing domain behavior. It defines the project vocabulary agents should use in code, tests and explanations.

## Local commands

Prefer Docker-based commands because the application depends on MySQL.

- Start dev stack: `make run`
- Detached dev stack: `make up-d`
- Stop dev stack: `make down`
- Enter web container: `make bash`
- Web logs: `make logs-web`
- Create migrations: `make makemigrations`
- Apply migrations: `make migrate`
- Backup database: `make backup`
- Restore database: `make restore file=<dump.sql>`

Inside the `web` container, use:

- Django checks: `python gym/manage.py check`
- Migration drift check: `python gym/manage.py makemigrations --check --dry-run`
- Tests: `python gym/manage.py test --noinput`
- Static dry run: `python gym/manage.py collectstatic --dry-run --noinput`
- Production deploy check: `python gym/manage.py check --deploy`

## Production and deploy constraints

- Production uses `docker-compose-prod.yaml`, `Dockerfile.prod`, `Dockerfile.nginx`, `config/entrypoint.prod.sh` and `cermed.conf`.
- Production config comes from `.env.prod` on the server only. Never commit `.env`, `.env.prod`, credentials, database dumps, media uploads or generated static output.
- The production workflow is GitHub Actions over SSH and server-side git/Compose operations. Do not switch it to rsync unless the user explicitly reopens that decision.
- Do not treat longer Nginx/Gunicorn timeouts as the primary fix for database write blocking. Prefer reducing lock scope, query count and duplicate submissions.

## Static, media and generated files

- Source static assets under `gym/*/static/` are meant to be tracked.
- `gym/staticfiles/` is `STATIC_ROOT`, generated by `collectstatic`, and must not be tracked.
- `gym/media/`, `media/`, `backup_data/` and `gym/backup_data/` are runtime data and must not be tracked.
- If a production static asset is missing, verify source assets, run/inspect `collectstatic`, then verify Nginx serving. Do not add generated `staticfiles` output to git.

## Coding and review rules

- Preserve user changes and unrelated work. Check `git status --short` before editing.
- Use Django built-ins and current repo patterns before adding dependencies.
- Keep view mutations on POST with CSRF protection. Avoid GET endpoints that mutate state.
- For database write bugs, build a tight repro first; then inspect transaction scope, query count, idempotency and duplicate submissions.
- For UI work, preserve Django template behavior and static asset paths. Prefer progressive enhancement over framework rewrites unless explicitly requested.
- Before handoff, run validation proportional to the change. For backend changes, at minimum run Django checks and targeted tests when available.

## Repo-local skills

This repo includes project-local skills under `.agents/skills/` so future agents can work without depending on a specific global Codex setup. Use the relevant skill when the task matches:

- `django-expert`: Django models, ORM, views, DRF, migrations, auth, production settings and performance.
- `frontend-design`: Django template/static UI work and visual polish.
- `diagnosing-bugs`: hard bugs, regressions, lock contention and failing production behavior.
- `tdd` and `python-testing-patterns`: test-first changes and Python/Django test strategy.
- `code-review`: review work-in-progress or branch diffs.
- `codebase-design`: module seams, refactors and testability improvements.
- `interface-design` and `web-design-guidelines`: product UI, accessibility and UX review.
- `domain-modeling`: vocabulary and ADR/context updates.
